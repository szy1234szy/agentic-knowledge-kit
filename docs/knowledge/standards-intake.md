# 接入已有编程规范

当你有团队编码规范、旧项目维护指南或个人复盘规则时，把资料路径或链接交给 Codex，并指定目标项目。让它使用 `$standards-intake` 对照当前代码、测试、规则和 ADR，找出哪些条款可直接沿用、哪些要调整或等待确认。

保留原始资料的位置和版本。在目标仓库只记录实际适用的规则、作用范围、例外、决策与验证办法。一份规范可以整理进现有工程手册的一个章节，并用多个 ID 定位有独立适用范围的条款。

```json
{
  "id": "RULE-MAINTAIN-001",
  "kind": "rule",
  "status": "proposed",
  "path": "docs/engineering.md",
  "section": "提交前的验证记录",
  "scope": ["src/**/*.py"],
  "origin": {
    "source": "团队代码修改与复盘规范",
    "revision": "2026-11-22",
    "locator": "修改完成后的交付 / 验证结果"
  }
}
```

## 何时会指导开发

提案可用 `trace RULE-MAINTAIN-001` 或显式 ID 查阅。负责人确认项目化条款、作用范围和例外后，将状态改为 `accepted`。此时 `context` 可按路径找到规则和来源，设计与验收时结合已有 ADR 与测试落实它。能够自动验证的部分可以在对应项目测试、lint 或 CI 中执行，适合人工核对的部分放进评审。

## 来源变了怎么维护

在 `review` 或规则审计中比较新旧版本。仅更新引用时保留理由，行为约束变化时提交提案，评审与当前实现的兼容性。旧规则被明确替代后，保留历史 ID 和替代关系。来源属于仓库外时，记录可识别的名称、版本或章节。外部资料本身的可访问性由对应资料系统维护。
