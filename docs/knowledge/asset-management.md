# 工程资产维护与归档

## 保持知识库可维护

1. **每次有意义的改动**用 `impact` 反查受影响记录。接口与行为变化检查功能现状，调用和数据流变化检查架构，配置和部署变化检查运维，验证方法或性能基线变化检查质量。只更新受影响的现行资料。
2. **定期审查**先看 `assets --core`，再运行 `assets --review`。默认把 180 天未核实的资产列为待复核，把登记了使用日期且满 365 天未再使用的低优先级资产列为归档候选。可用 `--review-days`、`--idle-days` 调整。缺少使用记录时由维护者调查，保留低频但关键的操作手册。
3. **重要版本**用 Git 标签或提交固定基线，复核核心架构、能力、部署和质量结果。需要交接或对外说明时，用 `project-view` 从该基线形成视图。

核心资产按影响和实用性选择，例如系统主入口、关键约束、常查的故障手册。核实内容后才记录 `last_reviewed`，在任务或排障中实际使用后才记录 `last_used`。已有文档可直接登记路径，减少内容重复。

## 复核证据和重复资料

核实时，把实际核实过的 Git 提交哈希放入 `asset.reviewed_commit`。运行 `review` 列出核心资料的证据锚点和基线后的相关变化。用 `review --id ARC-EXECUTION` 只看一项。基线缺失或不可用时，先对照当前代码、配置和最近通过的项目测试核实。

同类记录共享范围、文件证据或文档时会列出重叠候选。`review --all` 另可检查不同 Markdown 文件中的相同正文。人工复核用途与约束，保留有独立用途的资料。决定合并时，先迁移独有结论和当前引用，再按归档流程处理被取代的条目。

同一读者和任务通常可以共用一份文档，章节承担不同用途时可分别登记。合并保留原 ID，在索引中更新 `path` 与 `section`。严格校验会检查标题缺失或重复，知识查询显示指向的章节。

例如，把架构说明登记为核心资产，并用真实代码路径限定变更影响。以下文件名和日期供参考，接入时以项目实况填写。

```json
{
  "id": "ARC-EXECUTION",
  "kind": "architecture",
  "status": "implemented",
  "path": "docs/architecture/execution.md",
  "scope": ["execution/**"],
  "asset": {
    "importance": "core",
    "last_reviewed": "2026-11-22",
    "last_used": "2026-11-22"
  }
}
```

## 归档和恢复

1. 用 `assets --review` 查看候选，通过 `trace <ID>` 和仓库搜索复核依赖及文档链接。核心资产和仍支撑现行方案、约束或验收的记录优先修订。存在替代资料时先迁移现行引用。
2. 经确认后移动到 `docs/knowledge/archive/`，保留原 ID 和工程状态，更新 `path`、相对链接及 `asset.archive_reason`。在 Git 中一起审阅文件移动和索引改动。
3. 运行 `validate --strict` 与 `links`。单独检查归档文件时将路径传给 `links`。验证日常查询已省略该记录，并能用 `assets --archived`、`trace <ID>` 或显式 `context --id <ID>` 查回。

归档状态由文件位置和归档理由确定。常规证据审核及默认本地链接扫描面向现行资产，历史文件路径和索引关系仍须保持有效。恢复时将文档移回现行目录，更新路径和链接、去掉归档理由并复核证据。[归档目录说明](archive/README.md)
