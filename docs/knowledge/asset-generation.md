# 项目资产的生成与验收

从真实读者和任务出发。接手者要能跑起项目，开发者要能找到改动入口和不变量，值班人员要能定位故障。先选一个会反复发生或代价较高的任务，列出读者需要答对的问题，再检查现有资料能否支撑。

调用 `$project-bootstrap` 时可指定三种模式。**只审查**输出发现和建议。**增量优化**是默认方式，直接补有证据支持的缺口。**指定重写**只重组明确点名的文件或章节。修改时保留同一资产的 ID、有效的人工说明和历史依据。移动标题或路径时同步调整索引和链接。

## 默认写多少

未设置项目偏好时，一句「帮我生成项目资料」先覆盖一个代表性流程，可信且可找到的答案直接引用。需要补缺口时，默认只处理一份项目说明，先用现有 README 或概览，没有合适的说明再填写项目概览占位。索引按实际检索需要调整。

下表用于判断已选主题值得维护什么。架构详解、依赖故障分析或运维手册等专题由用户按需点名，或由项目偏好启用。先考虑原位补充。有独立用途和维护需要时再单独成文。

## 保存项目的建档偏好

需要长期关注某些内容时，在目标项目创建 `docs/knowledge/generation-preferences.md`。三个章节都可省略。下面是一个只深入检查订单提交失败行为的例子。

~~~markdown
# 项目建档偏好

## 关注功能
- 订单提交

## 专题
- 订单提交｜失败行为与恢复｜深入

## 验收问题
- 订单提交失败时，调用方收到什么结果？有哪些测试覆盖？
~~~

用「功能或范围｜主题｜简要或深入」逐行声明专题。简要聚焦当前行为和入口。深入补充与本功能有关的配置、失败分支、验证证据和缺口。只关心普通演示流程的项目可以省略「专题」。项目有可用性目标时，可把要核查的目标写进验收问题，生成结果仍需将期望、实现和验证情况写清楚。

之后说「帮我生成项目资料」会沿用偏好。本次明确限定功能、章节或深度时，以本次要求为准。说「本次只补项目概览」可以跳过偏好专题，移除某项专题可以停止后续展开。当前文档、索引 ID 和人工内容继续按正常方式维护。

## 中间件与故障影响

指令示例「用 `$project-bootstrap` 分析 Redis 在这个项目里服务哪些实际功能，以及 Redis 不可用时用户会看到什么」。也可以在长期偏好中启用，例如 `运行时命令｜Redis 依赖故障影响｜深入`。

只记录由实际调用证明的用途。同一依赖可能同时承担缓存、状态或健康探测，每种用途分别核对。专题优先追加到现有项目说明。可用一张表承载结论。

| 依赖与实际功能 | 启用条件和用途 | 不可用时的表现 | 证据与待验证 |
| --- | --- | --- | --- |
| 依赖名、调用入口、功能 | 配置开关、代码入口、承担的职责 | 业务能否继续、会丢失或延迟什么、监控能看到什么 | 配置和调用链接、异常或恢复路径、已执行验证和缺口 |

如果需要日常追踪，用 `architecture` 记录指向依赖章节，使用 `related_to` 连接已有的 Feature 或 Capability；两端的 `context --id <ID> --depth 1` 都能找到对方。将关键调用或配置列入 `scope` 或证据，用 `impact <改动的文件路径>` 找回需要复核的章节。只出现于配置的依赖先记为候选。评估用法时写明功能目标和代价，线上故障表现由相应环境的故障验证确认。

## 什么时候生成哪类资产

| 触发场景 | 优先产出 | 根据什么生成 |
| --- | --- | --- |
| 接手项目，主流程难以理解 | 一份项目说明。只有跨模块关系确实复杂时，再补架构说明 | README、运行入口、真实调用链、配置和一条代表性流程 |
| 功能契约或异常行为难以定位 | 在已有功能说明补输入、输出、边界和验证办法 | 实现、调用方、失败路径及契约测试 |
| 重要取舍会影响后续方案 | ADR 或既有决策记录的补充 | 已有设计讨论、PR、实测和适用约束。历史理由缺失时标为待核实 |
| 重复踩坑，或必须保护一项稳定条件 | 项目规则、不变量或回归证据 | 已确认的事故根因、契约、生产经验或可重放测试 |
| 部署、迁移、恢复容易出错 | 操作指引，写明开始条件、预期输出及回退入口 | 配置、脚本及实际运行记录 |
| 已有资料能完成同一个任务 | 补导航、合并重复章节，或保留原状 | 现行文档、索引和读者实际能找到的路径 |

## 生成步骤

1. **先写验收题。** 先从项目原有的快速开始定位产出核心结果的步骤，识别安装或初始化等前置动作。通用建档沿同一代表性流程核对实际入口和实现、成功与失败如何返回、直接覆盖该实现的测试。先只用现有资料回答，再从代码和测试断言核对缺口。
2. **再找证据。** 从一个真实入口读调用者、关键配置、至少一个适用的测试或失败路径。为会改变读者行动的结论记录实际路径、命令或出处。代码可以证明当前行为，历史动机需要决策记录或当事人证据。
3. **写最小可用正文。** 原位补现有章节或索引。只有读者任务、维护责任或更新时机明显不同才拆文件。每条正文讲清可观察行为、关键边界和下一步。把待确认的事实说清楚，已有等效说明时保留原文。
4. **按题复核。** 让读者从原文档入口找答案，再用代码、配置和真实输出校对。只指到入口测试时，仍需核对处理器行为真正由哪个测试覆盖。尚有缺口时报告部分完成，标明未通过题目和原因。需要执行的命令区分已执行和待执行。用 `validate --strict` 和 `links` 检查索引及引用。
5. **登记维护条件。** 新增或更新必要的 ID、章节、范围和证据。为核心资料注明哪些行为、配置或决策改变会触发复核。后续开发用 `impact` 提示候选，继续按读者问题判断是否改文档。

试点可以比较同一基线下生成前后能回答多少验收题、定位是否正确、有没有漏掉关键风险。首次自查记录为小样本走查。若要判断团队收益，用独立读者和多个真实任务复测。

操作手册优先让读者独立执行，包含前置条件、所在目录、命令、成功输出及首个排查入口。约束优先让开发者能判断是否违反，单条说明写明适用范围和具体证据。不同约束可作为同一份正文的多个章节分别登记，避免用一个测试支撑多条无关约束。

## 按用途生成三类常用资料

先写读者问题，再顺着同一条场景调查。工作过程中记录「待回答的问题、事实或假设、证据位置、核实方式、待确认项」，供选中的生成方式复用。源码说明当前行为，测试断言说明覆盖范围，运行记录只证明对应环境和输入下的结果。规范、契约或已接受决策用于判断哪些行为必须持续保证。只有独立维护确有需要时才新建文档，已有章节和知识 ID 可继续使用。

### 项目说明

| 要素 | 做法 |
| --- | --- |
| 什么时候用 | 接手仓库，或现有入口无法让读者找到代表性流程。通用建档默认使用。 |
| 要回答什么 | 项目提供什么结果，哪条流程交付这个结果，从哪里进入、改动和验证。 |
| 证据从哪找 | 从原 README、启动配置和可执行示例找到核心步骤，沿运行入口、调用和直接测试核对。前置安装或初始化只解释必要部分。 |
| 怎么验收 | 从原 README 或项目入口出发，能定位核心实现、描述结果和关键边界，并找到对应测试或可操作的验证办法。 |
| 什么时候复核 | 读者入口、代表流程、启动条件、关键结果或验证入口改变时。 |

### 功能契约

| 要素 | 做法 |
| --- | --- |
| 什么时候用 | 用户点名功能行为，或完成当前任务必须核实指定功能的输入、输出或失败边界。 |
| 要回答什么 | 明确调用者、输入和前置条件、正常和异常输出、状态变化，以及可观察的副作用。 |
| 证据从哪找 | 沿实际调用方、公开接口、处理器和返回映射追踪。读取该层测试断言。公开契约与实际行为冲突时分开记录来源和差异。 |
| 怎么验收 | 至少能以一个正常和一个相关异常场景预测调用方看到的结果，并定位承担该行为的实现与直接验证。无直接测试时说明验证缺口与可执行的验证方式。 |
| 什么时候复核 | 调用契约、处理器、返回映射、状态或相应测试改变时。 |

### 关键约束

| 要素 | 做法 |
| --- | --- |
| 什么时候用 | 当前任务可能触及已约定的安全、数据一致性或关键业务边界，或者用户要求整理必须遵守的规则。 |
| 要回答什么 | 哪个条件必须成立、约束谁、哪些情况适用或例外、哪层机制保障、怎样发现违反。 |
| 证据从哪找 | 先查正式契约、已采纳规范或已接受 ADR，再核对实现保障和回归断言。仅观察到代码或测试行为时写成现状或待确认候选。历史原因未知时标明待核实。 |
| 怎么验收 | 用一个满足条件的例子和一个违反场景，核对读者能判断边界，并找到实际保障机制或验证缺口。负责人确认后才登记为已接受的项目规则或不变量。 |
| 什么时候复核 | 约束依据、作用范围、例外、保障机制或保护测试发生变化时。 |
