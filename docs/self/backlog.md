### 中间件影响验收记录

目标使用 AgentOS Runtime `bb1dfed` 的隔离副本。通用建档复用了上轮留下的项目说明，Git 无变更。显式要求分析 Redis 后，原位补充 `docs/ARCHITECTURE.md` 和索引，新增 Markdown 文件数为 0。

| 验收场景 | 实际结果 |
| --- | --- |
| 从 Redis 和功能双向查询 | `context --id ARC-AGENTOS-REDIS --depth 1` 找到会话热状态投影和服务就绪探测。从两个功能 ID 各自查询都找到同一个 Redis 章节。三个记录通过严格校验。 |
| 按用途核对不可用影响 | 源码显示 Redis 自动配置需要客户端类和 `agentos.redis.enabled=true`。热状态投影与就绪探测有不同的失败传播方式。注入客户端写入异常时，热状态没有写入，投影阶段返回。注入探测连接异常时，就绪返回 HTTP 503，存活接口继续返回 UP。 |
| 修改调用路径后找到原章节 | 在副本中把 `RedisRuntimeStateStage.java` 的投影 TTL 由 30 分钟改为 25 分钟。`impact --base HEAD` 命中「Redis 与受影响功能」「会话热状态投影」两节。更新对应资料前严格同步检查报告 2 条待复核，复核并更新原文后报告 0 条。 |

故障注入使用临时 `RedisImpactReplayTest`。第一项使 `StringRedisTemplate.opsForValue()` 抛出运行时异常，确认投影阶段捕获且确实调用了客户端。第二项使 `getConnectionFactory()` 抛出异常，经过 Redis 探针、健康聚合、就绪服务和 HTTP 控制器检查状态。离线 Maven reactor 执行这两项测试，2 项通过。真实 Redis 宕机时的连接超时、流量切换和恢复行为仍待部署环境验证。业务原仓库没有写入，跨会话遵循率尚未测量。

## 建立文档生成质量回归

现有受控走查由同一 Agent 执行。补充独立会话测试，固定项目提交、安装版本、输入和评分问题。让读者先从资料寻找入口、关键约束和验证办法，再以代码与测试核对。记录答案正确性、关键遗漏、已有知识 ID 与人工说明的保留情况、无关产出和自动路由结果。保留基线供后续版本用同一规则比较。[已有建档验收](#本轮验收记录)

### 文档质量回归步骤

从两个 Git 提交分别建隔离副本，安装同一套件版本并提交安装后的初始状态。每个项目分别开一个新会话，只发送「帮我生成项目资料」。保存最终回复、`git status --short`、正文差异和索引差异。生成报告只用来记录过程，评分以持久化的文档为准。

再为每个项目准备两份仅读取文档的副本，分别对应生成前和生成后。移除源码、测试正文、Skill 文件和评分答案。每次评分用新会话，只提供阅读入口和验收题，要求逐题引用文档及标题，资料不够时标明缺口。维护者最后对照冻结的源码答案逐项给分。

| 项目与提交 | 阅读入口 | 预先冻结的验收问题和答案 |
| --- | --- | --- |
| AgentOS Runtime `bb1dfed` | `README.zh-CN.md` | ① 执行请求入口是 `RuntimeController.execute`。② `SUCCEEDED` 与 `DUPLICATE` 返回成功，其余状态映射失败。③ 修改 handler 的成功结果映射时，找 `RuntimeCommandHandlerTest`。 |
| 本套件旧版 `97465b8` | `README.md` | ① 升级从 `install.py --upgrade` 进入。② 已有项目索引和 `AGENTS.md` 由目标项目维护，升级不覆盖这些文件。③ 用 `scripts/test_install.py` 查安装边界的回归。 |

每题只有回答正确且文档引用可达才记 1 分，每个项目满分 3 分。另记自动路由是否有效、文件新增和原位修改数量、已有 ID 或有效人工内容是否丢失、是否出现无关专题。回复或日志缺失时将该轮记为未运行完成。后续版本按同一输入和判据比较，历史结果追加在此处。

## 改善跨模块知识检索

原有查询从路径和 ID 出发，依赖已登记的关系。先用真实任务区分遗漏是登记不足、影响范围写错，还是查询本身未能找到，再决定补记录、改指引或改工具。记录命中的重要资料、漏检项和无关候选量，确保关联结果可以追到具体路径或证据。[现有检索设计](records/adr-002.md)

v0.23 的 `context --query` 允许以登记的 ID、章节或计划标题为起点，沿用双向关系。AgentOS `bb1dfed` 隔离副本保留同一份经源码对照的六条索引，以通用 `application.yml` 为起点。基线只给路径，改动后同时给已知主题词并展开一层。Redis 热状态配置装配从 0/2 到 2/2，命中装配与存储验证。RabbitMQ 入站从 0/3 到 3/3，命中消费者、重复投递约束和测试。两次新查询无无关候选。本结果适用于已登记名称和关联的固定样例，异步业务流程本身未在此回归中重新运行。[查询实现](../../scripts/knowledge.py)

## 按章节复核知识同步

v0.22 的同步检查按文件判定是否更新。v0.23 为带 `section` 的记录补逐条判定。回归覆盖只更新一节、另一节附单条复核说明，以及无章节记录仍按文件复核。[现有同步检查实测](engineering-guide.md#如何验收同步说明)

v0.23 使用 Git 基线与工作区的 Markdown 章节正文判断是否更新。新回归在临时仓库中仅修改第一节的围栏示例，严格检查只提示第二节；追加第二节的 ID 复核说明或实际修改第二节后通过。无 `section` 的记录保持按文件判断。章节文字变化只能证明该章节被改过，事实仍由审阅确认。[同步回归](../../scripts/test_knowledge.py)

## 对齐发布版本与资料基线

任务开始时，本地包为 v0.22，工作区 Git 基线和项目说明仍引用 v0.16。v0.23 的正式 ZIP 由 Git 提交构建，`SOURCE-REVISION` 保存版本和完整提交。无 Git 引用时构建预览包。确定性打包在临时检出用同一提交连续执行两次，SHA-256 一致，版本清单与提交一致。两次均通过解压后的安装回归、索引、链接和套件测试。有远端发布安排时，核对远端可获取同一提交或标签。[项目说明](project-understanding.md) · [发布流程](engineering-guide.md#校验与发布)
