# project-view

## 适用原则
本 Skill 只负责自己的生命周期职责；其他知识类型与审批边界由项目 `AGENTS.md` 和 `docs/knowledge/README.md` 规定。

「帮我生成项目资料」属于 `project-bootstrap` 建档请求。派生视图用于明确的阅读、交接或展示需求；写入独立视图需要用户明确提出其持久化用途。


## 步骤
1. 明确阅读任务和信息边界。项目成员先看到用途、代表场景和工作主线，再补技术机制、限制和深入阅读链接。面试或公开展示保留适合该受众的事实。
2. 从项目概览、核心资产和任务入口选择一条代表性流程。用代码、配置、测试和已记录的决策逐步核对输入、状态、调用和输出。
3. 按「问题 → 对象 → 关系 → 机制 → 边界 → 反馈」组织项目理解。需要持久化时用 `docs/knowledge/templates/project-understanding.md`。针对具体问题时可以只输出相关环节。
4. 面向编码时，给出「修改目标 → 入口 → 适用约束或 ADR → 验证方式」。把能从代码核实的现状与决策理由分别注明来源。历史动机没有记录时标为待核实。
5. 区分本人贡献、团队贡献与 AI 帮助；禁止编造性能数据。
6. 用户需要可复用视图时，先在现有项目说明或工程手册补一节。视图有独立交付用途，再写入 `docs/knowledge/views/`，注明核实版本和范围，并链接原始知识记录。
   首读入口优先回答项目能帮读者做什么、该打开哪一节。用一个可复现的场景串起入口、结果和下一步，决策、故障及证据细节按需链接。
   版本快照用 Git 标签或提交标明基线，记录该版本的核心架构、部署条件、已验证能力和已知限制。根据实际版本复核内容后再写入。
7. 公司机密、凭据和受限实现不应未经允许对外发布。
