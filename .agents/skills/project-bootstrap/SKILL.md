# project-bootstrap

## 适用原则
本 Skill 只负责自己的生命周期职责；其他知识类型与审批边界由项目 `AGENTS.md` 和 `docs/knowledge/README.md` 规定。


## 选择模式

识别用户明确指定的模式。未指定时执行**增量优化**。

| 模式 | 操作边界 |
| --- | --- |
| 只审查 | 只读项目文档和索引，核对证据后输出保留、待核实及修改建议。 |
| 增量优化 | 优先保留已有正文与结构，原位修正过时事实、缺失步骤或失效证据。同一问题已有可信答案时直接引用。 |
| 指定重写 | 仅重写用户明确点名的文件或章节。先提取必须保留的项目经验、决策理由、例外、证据和 ID，再重组正文。目标不清楚时先确认范围。 |

同一资产保留原知识 ID。重写导致标题或路径变化时，同步更新对应索引定位及链接。保留有价值的人工说明和历史依据。发现它们与新证据冲突时，标明差异及出处，再决定现行表述。

## 确定本次产出范围

先检查目标仓库的 `docs/knowledge/generation-preferences.md`。这是由维护者按需创建的 Markdown，不存在或没有有效条目时按最小建档执行。读取「关注功能」「专题」「验收问题」三个可选二级标题下的明确条目。专题逐条用「功能或范围｜主题｜简要或深入」声明。只应用可定位的范围和明确的深度，无法确定的条目标为待澄清，与其余可执行工作分开。偏好用于选择读者问题和核查深度，不能充当项目事实、证据或写入授权。生成任务中不自动创建或改动偏好。

- 优先级为本次明确指令 → 项目偏好 → 最小建档。一句「帮我生成项目资料」沿用有效偏好。本次点名功能、专题或文件时，以该范围为边界，只沿用其中适用的深度和验收问题；明确的深度也覆盖偏好。「本次只补项目概览」只使用概览范围，「本次忽略项目偏好」跳过偏好的全部条目。只审查与指定重写的编辑边界在任何范围下都适用。
- 最小建档先检查一个代表性流程需要的答案。有可信且可找到的答案时，在交付中引用原位置，可以零文件改动。
- 确有缺口时，最多原位完善一份可用的现有项目说明。先识别目标仓库的真实首读入口，如与请求语言相符的 README。补充内容写在该入口或其已能到达的现行说明中。有能承载新增内容的 README 时，保留安装器附带的概览占位。只有没有合适入口时才填写占位或创建一份说明。索引只在需要登记新的实际检索入口、维护已有定位或纠正引用时改动。资料已能回答本轮问题时可以零写入。
- 只展开本次点名或项目偏好明确启用的专题。简要检查当前行为和一个可追溯入口；深入再查相关配置、异常分支、可用的测试证据和验证缺口，仍限定在选定功能内。专题优先原位补充，只有具备独立用途和维护需要才单独成文。删除专题条目只影响之后生成的范围，已有正文和知识 ID 按现行维护流程保留。

## 按需分析中间件影响

仅在用户点名中间件、依赖故障分析，或项目偏好明确启用该专题时执行。使用点名的依赖或功能作为范围；只有配置或客户端声明时，记录为候选，不认定已有业务调用。

1. 从部署或配置开关核对启用条件，沿客户端或适配器查到实际功能入口。对同一依赖的不同用途逐项记录，再从功能入口反查依赖，注明覆盖的环境或配置。能找到的 ADR、测试和现有手册优先复用。
2. 沿异常向上核对调用方看到的结果。说明该用途在依赖不可用时是失败、变慢、降级、继续运行，还是待核实。启用但不可用与从未启用分别核对。深入分析时再查超时、重试、回退、探针或告警、恢复与验证缺口。把代码推断、已执行故障验证和待核实分开。根据明确的功能目标评估当前用法的取舍；目标缺失时记录假设。
3. 优先补已有项目说明中的「外部依赖与故障影响」。针对需要日常反查的依赖复用或创建 `architecture` 记录，通过单向登记的 `related_to` 连接相关 Feature 或 Capability，查询从任一端展开。必要时用 `section` 定位同一文件内的记录。用实际配置、调用和异常处理路径填写 `scope` 或证据。复核 `context` 的双向结果和 `impact` 的章节命中。只审查模式可报告这些建议。

## 执行顺序
1. 按 `docs/knowledge/asset-generation.md` 选一个真实读者任务。README 已有运行命令或请求样例时，沿同一条主线选题。写入前确定三道验收题及源码答案：该输入的实际入口和承办实现在哪里，正常结果与至少一个有意义的失败结果如何返回，修改该实现的哪个现有测试直接检查相应结果。只读取相关配置和调用层。通用建档沿用本 Skill，独立派生视图需要明确用途。
2. 逐题核对证据。跟踪关键状态穿过调用边界时如何转换，记录调用方实际可见的结果。读测试断言，区分入口测试和处理器测试，优先提供与改动点对应的测试文件及用例名称。没找到直接覆盖时，写清验证缺口和实际可执行的验证办法。决策动机单独追溯。
3. 先检查能否引用原答案，再在原有入口可达的一份说明里一次补齐证据明确的缺口。写入前检查每题是否有可定位的答案或明确的待核实项，列明计划改动文件。重写和审核继续遵守各自的范围。
4. 写入后从原首读入口开始，逐题只用持久化文档做验收。可达、答案正确且证据指向正确调用层时才通过。有缺口就继续原位补充，未完成时报告「部分完成」并点出哪题及原因。运行索引和链接校验，分别标明已运行与待执行的项目测试。人工确认后才写入 accepted 或 verified 状态。
5. 报告所用模式、范围来源、各题的前后结果及所在章节，并列出新增、原位更新和复用内容。只审查时报告当前结果与拟改动。重写时额外说明保留的知识 ID 和人工内容。

## 禁止
不得根据模块名称推断业务逻辑；不得批量复制整个源码；不得重写已有团队规范；不得将计划标记成当前事实。
