# knowledge-sync

## 适用原则
本 Skill 只负责自己的生命周期职责；其他知识类型与审批边界由项目 `AGENTS.md` 和 `docs/knowledge/README.md` 规定。


## 步骤
1. 获取本任务 Git Diff、关联计划和实测结果。若基线对应本任务范围，运行 `python scripts/knowledge.py impact --base <基线提交>`；工作区有其他任务改动时，传入本任务实际涉及的路径。检查删除和重命名前后的引用。
2. 按变更性质复核知识：接口、行为或状态变化看功能现状。模块边界、调用链或数据流变化看架构。部署、配置或迁移脚本变化看运维。测试判据、评估方法或性能基线变化看质量。工作方式变化看工程指南。重要取舍检查 ADR，约束变化检查 Invariant 或 Rule。
3. 寻找既有记录，优先原位修订。正文可作为同一份说明的不同章节维护，登记独立记录时可用 `section` 定位。重要决策变更新建 ADR，用 supersedes 连接历史。
   已登记的依赖装配、业务调用或异常处理路径发生改变时，用 `impact` 定位依赖章节，核对各用途的启用条件和故障表现；沿关联功能检查影响。只复核已登记或本次明确委托的范围。
4. 在 `registry.json` 登记/更新 ID、适用范围、源文件和跨记录关系。
5. 对 proposed 约束必须由负责人批准，才变成 accepted；未执行的测试不得标记 verified。
6. 运行 `python scripts/knowledge.py validate --strict` 和相关项目测试，汇报文档冲突、缺证据和未决项。已验证记录应关联版本化证据文件或真实运行记录的网址。尚有未验收的前置功能时，先保留当前计划的非验收状态。
7. 在交付中按「行为变化 → 记录 ID → 新增 / 修订 / 复核 / 无需更新 → 理由 / 证据」列出知识差异。知识改动随代码一起评审。
8. 有功能计划时，在原记录补齐实现路径、提交或 PR、逐项验收结果与剩余工作。已实现待验证用 `implemented`，验收执行通过且有记录的证据后改为 `verified`。复核 `impact` 找出的关联计划。
9. 实际比对了记录与当前实现后才更新 `asset.last_reviewed`。如果核实内容对应一个已存在的 Git 提交，可同时登记 `asset.reviewed_commit`。本次确实引用该记录进行设计、验收或排障时，可记录 `asset.last_used`。文件改字无需刷新核实日期。
10. 主体流程、决策依据或编码入口有变化时，检查相应的项目理解视图。沿链接更新事实来源与受影响的导航，保留未变动的部分。
    用 `docs/knowledge/asset-generation.md` 中的读者任务检查更新是否足够。行为及读者操作无变化、已有资料仍可完成任务时，记录复核理由即可。
11. 含 Git 基线的任务运行 `sync-check --base <基线提交>` 检查受影响资产。普通记录按登记文件或章节检查。现行不变量和核心资产按 ID 提交本次的 `reason` 和可追溯的 `evidence`。删除、归档或降级也要保留原 ID 的复核理由及依据。新装工作流读取本次变更中的 `docs/knowledge/review.json`，本地可通过 `--review-file` 指定。即使已修改文档也要复核实际主张。

## 门禁
绝不因文档描述与代码不同就未经确认擅自修改高风险系统行为。
